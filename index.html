Flagship case study

Building it under real constraints.

The industrial setting is incidental. What matters here is how the system was architected, tested, broken, fixed, and shipped.

Problem Architecture Decisions Evaluation Failure analysis Deployment Results Repository

Problem

Three tools, no shared context.

An engineer troubleshooting a fault has to search technical manuals for the right procedure, pull live telemetry to check whether a reading is actually out of spec, and interpret a photo of a gauge or nameplate — usually switching between three separate systems to do it. None of those tools reason about the other two. The workflow needed one system that could hold all three sources of evidence at once and reason across them.

System architecture

Supervisor-led orchestration.

A query reaches a supervisor agent, which fans out to whichever specialists it actually needs — retrieval, telemetry, vision, or all three — then a report agent synthesizes their findings into one cited response.

Failure analysis

What broke, and why.

Four of the 30 eval cases failed. Understanding why matters more than the score — each one is a specific, implementable fix, not a vague weakness.

Ambiguous unit in spec check

Symptom

Agent received a pressure value with no explicit unit and defaulted to psi when bar was implied by context.

Fix

A unit-disambiguation step that prompts for confirmation before comparison.

Out-of-scope query, partial match

Symptom

A query about electrical grounding returned a partially fabricated citation from adjacent-but-irrelevant KB content.

Fix (implemented)

Explicit citation validation requiring the agent to say "not found in the knowledge base" rather than extrapolate.

Multi-parameter spec check

Symptom

A query with two simultaneous out-of-spec readings — the agent caught one and missed the second.

Fix

A loop in the spec-checker that runs once per detected parameter instead of terminating after the first match.

Contradictory inputs

Symptom

A query stated a reading was both within spec and dangerous — a known LLM failure mode under logical contradiction.

Fix

A consistency-validation step that flags and rejects contradictory inputs before tool execution.

Production readiness race condition (during AWS migration).

Symptom

The ALB marked the service healthy before application initialization — retrieval and agents — had actually finished loading.

Root cause

Process liveness and application readiness were being treated as equivalent.

Fix

An explicit is_ready flag returning 503 until the pipeline finishes initializing, plus grace-period tuning on the health check.

Lesson

Infrastructure health is not the same thing as application readiness.

Deployment

Off Spaces, onto AWS.

Originally deployed on Hugging Face Spaces, which sleeps on inactivity — not viable for anything meant to look production-oriented. Migrated to ECS Fargate behind an ALB, with ECR for images, S3 for ChromaDB persistence, Secrets Manager for API keys, and a GitHub Actions pipeline authenticated via OIDC. The migration surfaced real problems beyond the readiness race above: an empty knowledge base caused by .gitignore excluding data files (fixed via S3 hydration at startup), and a missing iam:PassRole permission that blocked the first deploy. HTTPS is deliberately deferred pending a purchased domain.

Results

What the numbers mean.

A full plant-wide audit — pulling readings, cross-referencing manuals, checking standards, writing a report — normally takes a qualified engineer an estimated 30 to 90 minutes. The multi-agent path completes the same audit in about 30 seconds for that specific workflow: roughly a 180× reduction against that estimate, not a claim about general system-wide speedup. For a single-equipment query, the single agent returns in 1–4 seconds; multi-agent orchestration is reserved for queries that genuinely span retrieval, telemetry, and safety at once.

On evaluation: 90% overall pass rate (29 of 30 cases), all 10 retrieval test cases passed, and 3.09s average latency across the suite. Full methodology and the raw eval log are in the repository.

Second case study — architecture transfer

Sequential handoff, where order matters.

You can't score a clause's risk before grounding it in a legal standard, and you can't recommend action before the risk is scored. LexAI enforces that order agent by agent. Legal is just where I happened to build it.

Why sequential

Each agent's output is the next agent's required input — the Risk Assessor cannot score without the Researcher's citations, and the Plain Language Specialist cannot recommend before risk is justified. Parallelizing this would mean merging incomplete, ungrounded outputs. Sequential isn't a limitation here; it's the correct model for how a law firm actually reviews a contract.

Risk detection

Fourteen risk patterns — unlimited liability, broad indemnity, one-sided termination, automatic renewal — are flagged by regex on every clause before any LLM call. These signals are handed to the agents as structured input, not discovered mid-reasoning, which is what lets the highest-risk clauses get prioritized when the input budget is constrained.

Current limits

The live demo runs on free-tier inference with a capped token budget, which limits full-contract coverage on longer documents — documented in the repo rather than hidden. Two config changes (removing the clause cap, upgrading the model tier) move this to full production coverage with no architectural change. That gap between demo-tier and production-tier is itself the kind of constraint I design for explicitly, not the kind I paper over.

Process

How I approach a new problem.

The same seven steps, whether the workflow is industrial, legal, or informational.

1

Understand the workflow

What task or decision are we actually improving?

2

Identify constraints

Data, latency, cost, security, reliability, human oversight.

3

Conventional software, RAG, tools, workflow, agent, or multi-agent system — in that order of preference.

4

What does success actually mean, in measurable terms?

7

Deploy and observe

Infrastructure, latency, cost, errors, and operational behavior.

Engineering principles

Working principles.

Each one tied to a specific decision, not left as a slogan.

Constraints first

Architecture follows constraints.

Cost, latency, data quality, and reliability determine architecture — I start there and work backward.

Evidence: hybrid retrieval was chosen because domain terminology made dense-only retrieval insufficient.
Evaluate before trusting

Evaluation precedes trust.

A system that hasn't been measured hasn't been proven to work — measurable pass/fail criteria come before assuming success.

Evidence: the 30-case eval suite was built before any optimization, to get an honest baseline.
Design for consequence, not just the answer

Failure modes are part of the architecture.

A wrong answer and a wrong action are not the same risk. The NORMAL / CAUTION / WARNING / CRITICAL severity gate exists because a shutdown recommendation needs a different confidence bar than a document lookup.

Evidence: contradictory-input detection added after a specific eval failure exposed the gap.
Design for operation

Deployment is part of engineering.

Containerization, observability, and reproducible deployment are considered from the start, not cleanup work at the end.

Evidence: migration from Hugging Face Spaces to AWS ECS Fargate behind an OIDC-authenticated CI/CD pipeline.
